Note 01 gave you the grammar. This note is about **fluency**: recognizing idioms fast enough that a 400-line PTX dump becomes a five-second read.

> The PTX in this note is representative nvcc / Triton output, trimmed and re-commented for readability (real dumps have tab-aligned operands and more redundant address math). The *shapes* are faithful — regenerate any of it yourself with the commands in the [chapter index](/cuda/09-ptx/).

## 1. Getting the artifact

```bash {filename="CUDA"}
nvcc -arch=sm_90 -ptx k.cu -o k.ptx
nvcc -arch=sm_90 -ptx -lineinfo -src-in-ptx k.cu    # CUDA source interleaved as comments
nvcc -arch=sm_90 -Xptxas -v -cubin k.cu             # + registers / spills / smem report
cuobjdump -ptx  libmylib.so                          # PTX already embedded in a binary
cuobjdump -sass -arch sm_90 k.cubin                  # what it actually becomes
```

```bash {filename="Triton / torch.compile"}
TRITON_KERNEL_DUMP=1 TRITON_DUMP_DIR=./dump TRITON_ALWAYS_COMPILE=1 python run.py
TORCH_LOGS=output_code python train.py    # see the Triton source Inductor generated first
```

```python {filename="Triton, in-process"}
compiled = add_kernel[(grid,)](x, y, out, n, BLOCK=1024)
with open('alpha_triton_PTX.ptx', 'w') as f:
    print(compiled.asm['ptx'], file=f)
print(compiled.asm["ptx"])
print(compiled.n_regs, compiled.n_spills)   # the numbers PTX itself won't tell you
```

## 2. Anatomy of an nvcc-emitted file

```ptx
//
// Generated by NVIDIA NVVM Compiler          ← nvcc, not Triton (Triton says "LLVM NVPTX Back-End")
// Cuda compilation tools, release 12.6
//
.version 8.5
.target  sm_90
.address_size 64
                                              ← module scope: __device__ globals, __constant__, extern smem
.visible .entry _Z6vecAddPKfS0_Pfi(...)       ← one block per __global__ kernel
{
    .reg ...                                  ← SKIP THIS
    ld.param ...                              ← prologue: unpack arguments
    mov.u32 %rX, %ctaid.x; ...                ← index computation
    ... body ...
    ret;
}
```

Four regions, always in this order. Your eyes should land on region 3.

## 3. Walkthrough 1 — bounds-checked vector add

```cpp {filename="vecadd.cu"}
__global__ void vecAdd(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}
```

```ptx {filename="nvcc -arch=sm_90 -ptx"}
.visible .entry _Z6vecAddPKfS0_Pfi(
    .param .u64 _Z6vecAddPKfS0_Pfi_param_0,          // const float* a
    .param .u64 _Z6vecAddPKfS0_Pfi_param_1,          // const float* b
    .param .u64 _Z6vecAddPKfS0_Pfi_param_2,          // float*       c
    .param .u32 _Z6vecAddPKfS0_Pfi_param_3           // int          n
)
{
    .reg .pred %p<2>;
    .reg .f32  %f<4>;
    .reg .b32  %r<6>;
    .reg .b64  %rd<11>;

    // ── prologue: parameters out of .param space ─────────────────────
    ld.param.u64  %rd1, [_Z6vecAddPKfS0_Pfi_param_0];
    ld.param.u64  %rd2, [_Z6vecAddPKfS0_Pfi_param_1];
    ld.param.u64  %rd3, [_Z6vecAddPKfS0_Pfi_param_2];
    ld.param.u32  %r2,  [_Z6vecAddPKfS0_Pfi_param_3];

    // ── global thread index ──────────────────────────────────────────
    mov.u32       %r3, %ctaid.x;
    mov.u32       %r4, %ntid.x;
    mov.u32       %r5, %tid.x;
    mad.lo.s32    %r1, %r3, %r4, %r5;      // i = blockIdx.x*blockDim.x + threadIdx.x

    // ── the guard, inverted ──────────────────────────────────────────
    setp.ge.s32   %p1, %r1, %r2;           // p1 = (i >= n)
    @%p1 bra      $L__BB0_2;               // branch OVER the body

    // ── address math ─────────────────────────────────────────────────
    cvta.to.global.u64 %rd4, %rd1;         // a as a global-window address
    mul.wide.s32       %rd5, %r1, 4;       // i * sizeof(float), s32 → s64 in one op
    add.s64            %rd6, %rd4, %rd5;   // &a[i]
    cvta.to.global.u64 %rd7, %rd2;
    add.s64            %rd8, %rd7, %rd5;   // &b[i]   (offset reused!)

    // ── the actual work ──────────────────────────────────────────────
    ld.global.f32 %f1, [%rd8];
    ld.global.f32 %f2, [%rd6];
    add.f32       %f3, %f2, %f1;

    cvta.to.global.u64 %rd9,  %rd3;
    add.s64            %rd10, %rd9, %rd5;  // &c[i]
    st.global.f32      [%rd10], %f3;

$L__BB0_2:
    ret;
}
```

Five things to internalize from this one kernel:

1. **Guards are inverted.** `if (i < n) { body }` becomes `setp.ge` + branch *over* the body. Always read `@%pN bra` as "skip".
2. **`mul.wide.s32 %rd, %r, 4`** is the scale-by-`sizeof`. `.wide` means s32 × s32 → s64, so it does the sign-extension and the multiply in one instruction. Seeing `mul.wide.u32` instead tells you the index was unsigned.
3. **`cvta.to.global.u64` per pointer** — the parameter is a generic pointer; the compiler narrows it once so the load can be `ld.global` instead of `ld`.
4. **The byte offset `%rd5` is computed once and reused** for `a`, `b`, and `c`. Common-subexpression elimination is visible at the PTX level.
5. **Load order is reversed** (`b` before `a`). PTX ordering is not execution ordering; ptxas reschedules anyway.

### The same kernel with `const __restrict__`

```cpp
__global__ void vecAdd(
    const float* __restrict__ a,
    const float* __restrict__ b,
    float* __restrict__ c,
    int n
)
```

The `const` + `__restrict__` qualifiers give the compiler stronger information about the input pointers:

* **`const`** → this kernel does not write through `a` or `b`.
* **`__restrict__`** → accesses through `a`, `b`, and `c` are assumed not to alias. (no other pointer in the kernel argument points to same address, so, writing to any other pointer cannot change the value of `*a` or `*b`. So, we can pre-load values from `a` and `b` and keep them in registers without worrying about them being changed by a write through `c`.)

That extra information can allow `nvcc` to generate read-only-cache loads:

```ptx
ld.global.nc.f32  %f1, [%rd8]; // .nc appears
ld.global.nc.f32  %f2, [%rd6];
```

Here, **`.nc` means non-coherent**: the **`load uses the read-only/texture cache path`** (corresponding to `LDG`-style loads in SASS `__ldg`), rather than the normal global-load path.

The important point is that **`__restrict__` itself does not mean "use `.nc`"**. It gives the compiler aliasing information; `const` gives it read-only information; together they may enable this optimization (and the compiler may choose it or not depending on architecture and optimization).

> [!IMPORTANT] **PTX insight:**
> - C++ qualifiers such as `const` and `__restrict__` usually disappear from PTX as explicit syntax, but their effects can survive as different instructions such as `ld.global.nc`. This is a good example of how examining PTX can reveal optimizations that aren't obvious from the original C++.
> - The compiler's decision to use `.nc` depends on its analysis and the target architecture/compiler; don't treat `.nc` as a mechanical proof that `const __restrict__` was present.

## 4. Walkthrough 2 — a grid-stride loop with vectorized loads

```cpp
__global__ void saxpy4(float4* __restrict__ y, const float4* __restrict__ x,
                       float alpha, int n4) {
    for (int i = blockIdx.x*blockDim.x + threadIdx.x; i < n4; i += blockDim.x*gridDim.x) {
        float4 xi = x[i], yi = y[i];
        yi.x = fmaf(alpha, xi.x, yi.x);  yi.y = fmaf(alpha, xi.y, yi.y);
        yi.z = fmaf(alpha, xi.z, yi.z);  yi.w = fmaf(alpha, xi.w, yi.w);
        y[i] = yi;
    }
}
```

```ptx
    mad.lo.s32   %r10, %r7, %r8, %r9;      // i
    setp.ge.s32  %p1, %r10, %r2;
    @%p1 bra     $L__BB0_3;                // loop guard (zero-trip check)

    mov.u32      %r11, %nctaid.x;
    mul.lo.s32   %r1, %r8, %r11;           // stride = blockDim.x * gridDim.x  (loop-invariant, hoisted)

$L__BB0_2:                                  // ◄── LOOP BODY starts here
    mul.wide.s32 %rd5, %r10, 16;           // i * sizeof(float4)
    add.s64      %rd6, %rd3, %rd5;
    add.s64      %rd7, %rd4, %rd5;
    ld.global.nc.v4.f32 {%f1,%f2,%f3,%f4}, [%rd7];      // 128-bit vector load
    ld.global.v4.f32    {%f5,%f6,%f7,%f8}, [%rd6];
    fma.rn.f32   %f9,  %f1, %f17, %f5;     // four independent FMAs
    fma.rn.f32   %f10, %f2, %f17, %f6;
    fma.rn.f32   %f11, %f3, %f17, %f7;
    fma.rn.f32   %f12, %f4, %f17, %f8;
    st.global.v4.f32 [%rd6], {%f9,%f10,%f11,%f12};      // 128-bit vector store
    add.s32      %r10, %r10, %r1;          // i += stride
    setp.lt.s32  %p2, %r10, %r2;
    @%p2 bra     $L__BB0_2;                // ◄── back edge

$L__BB0_3:
    ret;
```

**How to find a loop in any PTX file:** find a `bra` whose target label is *above* it. Everything between the label and the back edge is the body.

What this dump tells you:
- `ld.global.nc.v4.f32` / `st.global.v4.f32` → **128-bit transactions**, the widest the hardware offers. If you expected vectorization and see four separate `ld.global.f32` instead, your `float4` alignment or aliasing proof failed.
- `fma.rn.f32` (not `mul` + `add`) → contraction happened, one rounding step.
- `mul.lo.s32 %r1, ...` was **hoisted above the label** → loop-invariant code motion worked.
- Only one `mul.wide.s32` per iteration → the compiler did *not* strength-reduce to pointer increments; ptxas usually will.

## 5. Walkthrough 3 — shared memory, barriers, warp shuffles

```cpp
__global__ void blockSum(const float* __restrict__ in, float* out, int n) {
    extern __shared__ float s[];
    int t = threadIdx.x;
    float v = (blockIdx.x*blockDim.x + t < n) ? in[blockIdx.x*blockDim.x + t] : 0.f;
    // warp reduce
    for (int off = 16; off; off >>= 1) v += __shfl_down_sync(0xffffffff, v, off);
    if ((t & 31) == 0) s[t >> 5] = v;
    __syncthreads();
    if (t < 32) {
        v = (t < blockDim.x/32) ? s[t] : 0.f;
        for (int off = 16; off; off >>= 1) v += __shfl_down_sync(0xffffffff, v, off);
        if (t == 0) atomicAdd(out, v);
    }
}
```

The PTX fingerprints:

```ptx
// extern __shared__ float s[]  →  an unsized extern array at module scope
.extern .shared .align 4 .b8 _ZZ8blockSumPKfPfiE1s[];

    // __shfl_down_sync(0xffffffff, v, 16)
    shfl.sync.down.b32  %f2|%p3, %f1, 16, 31, -1;   // 31 = clamp/segmask, -1 = 0xffffffff
    add.f32       %f3, %f1, %f2;
    // ... repeated for 8, 4, 2, 1 — the compiler fully unrolled the reduction loop

    // if ((t & 31) == 0) s[t>>5] = v;
    and.b32       %r5, %r1, 31;
    setp.ne.s32   %p4, %r5, 0;
    @%p4 bra      $L__BB0_4;
    shr.u32       %r6, %r1, 5;
    shl.b32       %r7, %r6, 2;
    mov.u32       %r8, _ZZ8blockSumPKfPfiE1s;   // base address of the smem array (32-bit!)
    add.s32       %r9, %r8, %r7;
    st.shared.f32 [%r9], %f7;
$L__BB0_4:

    bar.sync      0;                        // __syncthreads()

    atom.global.add.f32  %f20, [%rd6], %f19;   // atomicAdd(out, v)
```

Idioms worth memorizing:

| PTX | CUDA source |
|---|---|
| `bar.sync 0;` | `__syncthreads()` |
| `bar.warp.sync -1;` (`-1` = `0xffffffff`) | `__syncwarp()` |
| `shfl.sync.down.b32 d\|p, a, b, c, mask` | `__shfl_down_sync` — the `\|p` output is "was the source lane in range" |
| `shfl.sync.idx / .up / .bfly` | `__shfl_sync` / `__shfl_up_sync` / `__shfl_xor_sync` |
| `st.shared.f32 [%r9], %f` with a **32-bit** address | shared memory addresses are 32-bit window offsets, not 64-bit pointers |
| `mov.u32 %r8, <smem symbol>` | taking the base address of a shared array |
| `atom.global.add.f32` | `atomicAdd` on a global float |
| `red.global.add.f32 [%rd], %f;` | `atomicAdd` whose **return value was unused** — a cheaper reduction op |
| `vote.sync.ballot.b32` | `__ballot_sync` |
| `activemask.b32` | `__activemask()` |

> [!IMPORTANT] Understanding ptx instruction `shfl.sync.down`
> ```
> shfl.sync.down.b32 %f2|%p3, %f1, 16, 31, -1;
> ```
> - `-1 is __activemask() = 0xffffffff`
> - `31` is the clamp/segmask (the maximum lane index to read from).
> - and this is what it means in C++:
> ```cpp
> source_lane = lane_id + 16;
> 
> if (source_lane <= 31) {
>     f2 = value_of_f1_from(source_lane);
>     p3 = true;
> } else {
>     p3 = false;
> }
> ```


> [!TIP]
> **`atom` vs `red`**: `atom` returns the old value, `red` does not. If you write `atomicAdd(p, v);` and ignore the result, the compiler emits `red`, which does not need a round-trip and is meaningfully faster. If you see `atom` where you expected `red`, someone is capturing a return value they don't need.
>
> **`atom` (Atomic Operation)**
> - Performs the operation at the memory address and **returns the previous value** to a register.
> - Requires a destination register: `atom.global.add.u32 d, [a], b;` — `d` receives the old value.
>
> **`red` (Reduction Operation)**
> - Performs the operation at the memory address **without returning the old value**.
> - No destination register needed: `red.global.add.u32 [a], b;`

## 6. Reading Triton-emitted PTX

Triton's PTX comes out of the **LLVM NVPTX backend**, not NVVM, and it looks different:

```ptx
//
// Generated by LLVM NVPTX Back-End
//
.version 8.3
.target sm_90a
.address_size 64

.visible .entry add_kernel(...)
.reqntid 128, 1, 1                        // ← num_warps=4 → 128 threads. Always present.
```

Structural differences from nvcc output:

| | nvcc | Triton |
|---|---|---|
| Kernel name | C++ mangled | plain Python function name |
| `.reqntid` | only with `__launch_bounds__` | **always** (`num_warps × 32`) |
| Register declarations | modest | often hundreds — one block = many registers per thread |
| Masking | branches or predicates | almost always **predicated** `@%p` loads/stores |
| Loops | mirror your `for` | often fully unrolled by `BLOCK_SIZE` |
| Barriers | where you wrote them | `bar.sync 0` inserted by the layout/pipeliner |
| Shared memory | your `__shared__` | `.shared .align 16 .b8 global_smem[N];` — one arena Triton sub-allocates |

> [!IMPORTANT]
> `blockdim` in CUDA & `BLOCKSIZE` in Triton are **not the same**. Triton uses `BLOCK_SIZE` to mean "elements per block", not "threads per block".
> The compiler then chooses a `num_warps` and derives the thread count from that. If you see `reqntid 128,1,1` for a `BLOCK_SIZE=1024`, that means 128 threads are each processing 8 elements.
> ```python
> compiled = add_kernel[(grid,)](x, y, out, n, BLOCK=1024, num_warps=8)
> ```
> - with `num_warps=8`, so total threads = 8 warps × 32 threads/warp = 256 threads. Each thread processes BLOCK_SIZE / total_threads = 1024 / 256 = 4 elements.
>
> - Even though in triton, we write kernel on block level, but ptx is lowered to thread level instruction. Since in above case, each thread needs to process 4/8 elements (depending on `num_warps`), so we will see vectorized load/store in ptx (`.v4`).
>
> - if each threads has to process 8 elements, it can at max vectorize 4 elements, so we will have 2 vectorized load/store instructions (`.v4`), and idx will be incremented by `BLOCK_SIZE/2` (i.e. 512) for next vectorized load/store instruction.

### A masked, vectorized Triton load

```python
@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid  = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask, other=0.0)
    y = tl.load(y_ptr + offs, mask=mask, other=0.0)
    tl.store(out_ptr + offs, x + y, mask=mask)
```

```ptx {filename="BLOCK=1024, num_warps=4"}
    mov.u32      %r13, %tid.x;
    shl.b32      %r14, %r13, 3;          // tid * 8   ← 1024 elems / 128 threads = 8 per thread
    and.b32      %r15, %r14, 1016;       // keep it inside the block
    mov.u32      %r16, %ctaid.x;
    shl.b32      %r17, %r16, 10;         // pid * 1024   (BLOCK is a power of two → shift)
    or.b32       %r18, %r17, %r15;       // offs base for this thread
    ld.param.u32 %r19, [add_kernel_param_3];
    setp.lt.s32  %p1, %r18, %r19;        // mask = offs < n
    setp.lt.s32  %p2, %r20, %r19;        // ... one predicate per vector group

    mul.wide.s32 %rd8, %r18, 4;
    add.s64      %rd1, %rd5, %rd8;

    mov.u32      %r1, 0x0;               // ◄── `other=0.0` materialized BEFORE the load
    mov.u32      %r2, 0x0;
    mov.u32      %r3, 0x0;
    mov.u32      %r4, 0x0;
    @%p1 ld.global.v4.b32 { %r1, %r2, %r3, %r4 }, [ %rd1 + 0 ];   // ◄── predicated vector load
    @%p2 ld.global.v4.b32 { %r5, %r6, %r7, %r8 }, [ %rd1 + 16 ];
    ...
    add.f32      %f17, %f1, %f9;
    ...
    @%p1 st.global.v4.b32 [ %rd3 + 0 ], { %r33, %r34, %r35, %r36 };
```

Four Triton signatures to burn in:

1. **`mov.u32 %rN, 0x0;` immediately before a predicated load** — that is `other=`. If the lane is masked off the register keeps this value.
2. **`@%pN ld.global.v4.b32 { ... }, [ %rd + off ];`** with the roomy `{ }` and `[ ]` spacing — LLVM NVPTX's print style. Vectorization width here tells you whether Triton coalesced your access pattern.
3. **`shl.b32 %r, %tid.x, 3`** — the elements-per-thread factor (here 8). `BLOCK / (num_warps*32)` should equal it; if it doesn't, your layout isn't what you think.
4. **`.b32` types everywhere** — Triton loads as bits and reinterprets, so don't expect `.f32` on the load itself.

### The grep table for Triton kernels

```bash
grep -c 'ld.global'          k.ptx    # how many distinct global loads
grep -o 'ld.global[^ ]*'     k.ptx | sort | uniq -c   # widths & qualifiers at a glance
grep -E 'ld.local|st.local'  k.ptx    # SPILLS — the #1 Triton perf bug
grep -E 'mma|wgmma|tcgen05'  k.ptx    # did tl.dot hit tensor cores?
grep -E 'cp.async'           k.ptx    # is the loop software-pipelined?
grep -E 'mbarrier|elect.sync' k.ptx   # TMA / warp-specialized path
grep -c 'bar.sync'           k.ptx    # barrier count (layout conversions cost these)
grep -E 'div.rn|sqrt.rn|ex2' k.ptx    # numerics: precise vs approximate
```

> [!IMPORTANT]
> **Spills are the single most common Triton performance bug.** They appear as `st.local` / `ld.local` in PTX and as non-zero `compiled.n_spills`. Cause is almost always a `BLOCK_SIZE` (or `num_stages`) too large for the register budget. Fix by shrinking the block, lowering `num_stages`, or raising `num_warps` so each thread owns fewer elements.

### When `tl.dot` becomes tensor cores

```python
acc = tl.dot(a, b, acc)      # a: (128,64) fp16, b: (64,256) fp16
```

| Target | What you'll grep | Notes |
|---|---|---|
| sm_80/sm_86 | `mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32` | plus `ldmatrix.sync.aligned.m8n8.x4.shared.b16` feeding it |
| sm_90a | `wgmma.mma_async.sync.aligned.m64n256k16.f32.f16.f16` + `wgmma.fence` / `wgmma.commit_group` / `wgmma.wait_group` | operands via **shared-memory descriptors**, not registers |
| sm_100a | `tcgen05.mma.cta_group::1.kind::f16` + `tcgen05.alloc` / `tcgen05.ld` / `tcgen05.commit` | accumulator lives in **tensor memory**, not registers |

If you see plain `fma.rn.f32` in a loop where you expected `mma`, `tl.dot` fell back to FMA — usually because a dimension was below the minimum tile (`M`, `N` ≥ 16 and `K` ≥ 16), the dtype isn't tensor-core-supported, or `allow_tf32`/input precision settings forced it. [Note 04](/cuda/09-ptx/04-compute-and-tensor-cores.md) covers the whole family.

## 7. Mapping PTX back to source

```bash
nvcc -lineinfo -src-in-ptx -ptx k.cu     # CUDA source lines as comments inside the PTX
```

```ptx
	//// --- Begin inline source ---
	//// 12  if (i < n) c[i] = a[i] + b[i];
	//// --- End inline source ---
	.loc	1 12 9
	setp.ge.s32 %p1, %r1, %r2;
```

`.loc <file> <line> <col>` is the same metadata Nsight Compute uses for its Source page. Triton emits `.loc` too (disable with `TRITON_DISABLE_LINE_INFO=1` if the noise gets in the way), which is how you map a hot SASS line back to a line of Python.

> `.loc` is a PTX debug directive, not an executable instruction. It associates generated PTX instructions with source locations for debugging/profiling. It does not generate a SASS instruction.

## 8. The review checklist

Run down this list every time you open a PTX dump for performance reasons:

| Question | What to grep | Good sign |
|---|---|---|
| Did loads vectorize? | `ld.global` widths | `.v4.f32` / `.v4.b32` (128-bit), not 4× scalar |
| Read-only path used? | `ld.global.nc` | `.nc` present for inputs never written |
| Any spills? | `ld.local`, `st.local` | **none** |
| Mask → predicate or branch? | `@%p ld.` vs `bra` | predicate for short regions |
| FMA contraction? | `fma.rn.f32` vs `mul`+`add` | `fma` |
| Numerics as intended? | `div.rn` vs `div.approx`, `ex2.approx` | matches your precision requirement |
| Tensor cores engaged? | `mma`/`wgmma`/`tcgen05` | present for any GEMM-shaped kernel |
| Async pipeline? | `cp.async`, `mbarrier`, `cp.async.bulk` | present in a tiled loop on sm_80+ |
| Atomics minimal? | `atom` vs `red` | `red` when the result is unused |
| Barrier count sane? | `bar.sync` | one per real dependency, not per layout shuffle |
| Loop unrolled? | repeated bodies between labels | matches your `#pragma unroll` intent |
| Constant folding? | literals vs runtime math | shapes known at compile time became immediates |

> `div.rn` v/s `div.approx` is a common source of confusion. The table below summarizes the differences:
|                                              | `div.rn`                            | `div.approx`              |
| -------------------------------------------- | ----------------------------------- | ------------------------- |
| Accuracy                                     | High / correctly rounded            | Approximate               |
| IEEE rounding guarantee                      | Yes                                 | No                        |
| Typical use                                  | Numerical correctness               | Performance-tolerant math |
| Can use reciprocal approximation internally? | Compiler may optimize where allowed | Explicitly allowed        |

## 9. What you must **not** conclude from PTX

| Tempting conclusion | Why it's wrong | Where to actually look |
|---|---|---|
| "It declares 200 registers → high pressure" | Virtual registers, pre-allocation | `nvcc -Xptxas -v`, `compiled.n_regs` |
| "Fewer PTX instructions → faster" | ptxas rewrites, fuses, unrolls, predicates | SASS instruction count, `ncu` |
| "This PTX loop isn't unrolled" | ptxas unrolls independently | SASS |
| "These two loads are far apart, so latency is hidden" | PTX order ≠ issue order | SASS + `ncu` warp-stall reasons |
| "No bank conflicts — I checked the PTX" | PTX has no bank concept | `ncu` shared-memory tables |
| "It's memory-bound, I can see the loads" | Ratio depends on real issue rates | `ncu` roofline / SOL sections |
| "PTX shows no L2 hint, so caching is default" | ptxas and the driver add their own policies | `ncu` memory chart |

PTX is a **semantics** microscope. Every performance conclusion has to be confirmed one layer down.

## 10. The workflow that actually pays

```bash
# 1. baseline
nvcc -arch=sm_90 -ptx k.cu -o before.ptx

# 2. make ONE change (add __restrict__, change a block size, reorder a loop)

# 3. diff
nvcc -arch=sm_90 -ptx k.cu -o after.ptx
diff -u before.ptx after.ptx | less
```

Diffing is where PTX earns its keep. Absolute reading is slow and ambiguous; a diff isolates exactly what your change bought — `.nc` appeared, `.v4` appeared, an `ld.local` vanished, `fma` replaced `mul`+`add`, a branch became a predicate.

The same works for Triton: dump PTX for two autotune configs and diff them to see *why* one won.

## Interview Questions & Answers

### Q: You see `ld.global.f32` four times in a row on consecutive addresses instead of one `ld.global.v4.f32`. What are the likely causes?

**Answer:** Vectorization requires the compiler to prove (a) the addresses are contiguous, (b) the base is 16-byte aligned, and (c) nothing aliases in between. The usual culprits are: the pointer isn't declared `float4`/`__align__(16)` so alignment can't be proven; missing `__restrict__` so a possible write-through-another-pointer sits between the loads; a runtime stride the compiler can't fold to 1; or an element type whose 4-wide form exceeds 128 bits. In Triton the analogue is a non-contiguous last dimension or a block size that makes each thread own fewer than 4 contiguous elements. Fix the provable property, re-dump, and diff.

### Q: A Triton kernel is slow and `compiled.n_spills` is 40. What does the PTX show and what do you change?

**Answer:** PTX will contain `st.local` / `ld.local` pairs around the hot region — `.local` is per-thread memory backed by device DRAM, so every spill is a global-memory round trip inside your inner loop. The fix is reducing live values per thread: shrink `BLOCK_SIZE_M/N/K`, reduce `num_stages` (each pipeline stage holds another buffer live), or increase `num_warps` so the same block is spread over more threads. Verify by re-dumping and confirming `.local` disappeared and `n_spills` is 0 — and then confirm with wall-clock, because occupancy can move the other way.

### Q: How do you tell from PTX alone whether a kernel was compiled with `-use_fast_math`?

**Answer:** Look at the transcendental and division opcodes. Fast math turns `div.rn.f32` into `div.approx.f32`, `sqrt.rn.f32` into `sqrt.approx.f32`, and expands `expf`/`log`/`sin` into `ex2.approx.f32` / `lg2.approx.f32` / `sin.approx.f32` sequences — often preceded by a multiply by a magic constant like `0f3FB8AA3B` ($\log_2 e$). It also adds `.ftz` to many f32 ops (denormals flushed) and makes FMA contraction more aggressive. The `.approx`/`.ftz` modifiers are the tell; they're a modifier, not a separate instruction, so grep for them rather than for instruction names.

> [!NOTE] **`.ftz` (Flush-To-Zero)**
> 
> **`.ftz`** tells the GPU to treat **subnormal (denormal) `f32` values as zero**. Subnormals are values smaller than the smallest positive *normal* `f32` ($\approx 1.175 \times 10^{-38}$) and exist to provide gradual underflow near zero.
> 
> With `.ftz`, subnormal inputs/results are flushed to $\pm 0.0$ instead of being preserved. This can improve performance on hardware where subnormal arithmetic is expensive, at the cost of losing precision for extremely small values.
> 
> ```ptx
> mul.f32      %f2, %f0, %f1;   // preserves subnormals
> mul.ftz.f32  %f2, %f0, %f1;   // flushes subnormals to ±0.0
> ```
> 
> - **Mental model:** `.ftz` = *“I don't care about values this tiny; treat them as zero.”*


### Q: Why does Triton PTX put `mov.u32 %r1, 0x0;` before a predicated load, and what breaks if you write `tl.load(p, mask=m)` with no `other`?

**Answer:** A predicated load leaves the destination register **unmodified** when the predicate is false, so Triton must pre-initialize it with the `other` value; those `mov`s are that initialization. With no `other=`, Triton defaults it to zero for most cases — but the important consequence is that the *address* is still formed for masked-off lanes. That address must be safe to compute (it isn't dereferenced, but overflowing pointer math is still undefined), which is why the idiomatic Triton pattern clamps offsets as well as masking them when the tail could run far past the buffer.
